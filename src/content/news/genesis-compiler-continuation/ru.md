В [записи Evidence от 7 сентября 2026 года](https://genesis.evox.group/evidence/compiler-continuation/) описывается передача компилятора от **GLM 5.2 к DeepSeek V4 Flash** без переноса контекста беседы предыдущего агента. Принятое дерево исходного кода и родословная Git остались доступны. Инженерный вопрос заключается в том, что именно принимающая модель может проинспектировать и как можно оценить последующие изменения.

![Проект компилятора, сохраненный при смене наборов инструментов](./compiler-model-handoff.webp)

В записи сообщается о **1 820 из 1 820 сохраненных пройденных тестов LLVM SingleSource** после продолжения работы, а также об увеличении глубины рекурсии задач с 4 до 8. В ней не публикуется стенограмма по каждому исправлению, а также объем добавленного кода и стоимость этапа продолжения. Приведенные ниже публичные исходные коды jcc объясняют интерфейсы компилятора и механизмы регрессии; их отдельный снимок не восстанавливает точную последовательность действий при передаче.

## Унаследованный компилятор имеет границы, которые преемник должен соблюдать

[Архитектура jcc](https://github.com/EMI-Group/genesis-demo-jcc/blob/a8c116ec7ed3d59479ad3be8fed3e63384f50a87/docs/architecture.md) разделяет фронтенд, типизированное промежуточное представление CIR, оптимизатор, бэкенд машинного кода, ассемблер и драйвер командной строки. Фронтенд передает проверенное синтаксическое дерево на этап понижения (lowering); последующие стадии потребляют полученное представление, а не интерпретируют исходный код заново и независимо.

Это имеет значение, когда новая модель изменяет один компонент. Исправление арифметики при понижении все равно должно соответствовать типизации CIR; изменение соглашения о вызовах должно согласовываться с распределением регистров и выдачей объектного кода. Это примеры зависимостей, задокументированных в архитектуре, а не утверждения о конкретных исправлениях при передаче.

Драйвер предоставляет промежуточные точки остановки: `-E` для препроцессинга, `-emit-jcc-ir` для CIR, `-S` для ассемблера и `-c` для выдачи объектного кода. Эти артефакты помогают определить, какая стадия изменилась, перед тестированием скомпонованного исполняемого файла.

## Регрессионные проверки охватывают корректные программы и намеренные отказы

[Руководство по тестированию](https://github.com/EMI-Group/genesis-demo-jcc/blob/a8c116ec7ed3d59479ad3be8fed3e63384f50a87/docs/testing.md) описывает случаи «компиляция и запуск», которые проверяют статус выхода и результат, наряду со случаями «ошибка компиляции», проверяющими критичность диагностики, сообщение и диапазон в исходном коде. Проходы оптимизации также имеют проверки верификации представления.

Таким образом, у преемника есть более одного условия приемки. Генерации исполняемого файла недостаточно, если меняется результат его работы; принятия программы недостаточно, если политика языка требует ее отклонения. Тестирование диагностики сохраняет поведение, которое было бы упущено в бенчмарке, ориентированном только на успешное выполнение.

[README с версиями](https://github.com/EMI-Group/genesis-demo-jcc/blob/a8c116ec7ed3d59479ad3be8fed3e63384f50a87/README.md#feature-status) перечисляет конкретные ограничения, такие как частичная арифметика `long double` и отложенные целевые платформы. Эти ограничения являются полезной унаследованной информацией: изменение задокументированного отказа является решением по функциональности, а не автоматическим исправлением регрессии.

## Что на самом деле сравнивает тестовая среда LLVM

Публичный [раннер LLVM-suite](https://github.com/EMI-Group/genesis-demo-jcc/blob/a8c116ec7ed3d59479ad3be8fed3e63384f50a87/tools/llvm-suite/run.py) настраивает набор тестов с проверяемым компилятором, собирает исполняемые файлы и сравнивает их вывод с эталонными файлами. Прямое сравнение основано на токенах, разделенных пробелами: нечисловые токены должны совпадать точно; для числовых токенов используется настраиваемый допуск с плавающей запятой (по умолчанию 1e-4); финальный код выхода должен совпадать точно.

Это иллюстрирует, почему для подсчета тестов необходим манифест и политика сравнения. Задокументированное подмножество Regression/C из 36 случаев в раннере — это иная область оценки, отличная от 1 820 сохраненных случаев в записи о продолжении. Малый снимок нельзя использовать для вывода о начальном уровне прохождения тестов при передаче, а вычитание двух итоговых значений не позволит измерить прогресс.

## Соотносите отчетный результат передачи с его областью охвата

| Переход модели | GLM 5.2 → DeepSeek V4 Flash |
| Перенесенный контекст беседы | 0 |
| Сохраненное состояние проекта | Принятая родословная компилятора |
| Глубина рекурсии задач | 4 → 8 |
| Финальная оценка | 1 820/1 820 сохраненных случаев LLVM SingleSource |

Источник: [GW-000002](https://genesis.evox.group/evidence/compiler-continuation/). Это отчетные результаты проекта по одной передаче. Глубина рекурсии описывает декомпозицию задач; результат теста предоставляет доказательство поведения.

Записи о первичном компиляторе и продолжении ссылаются на один и тот же репозиторий. Их не следует считать двумя независимыми проектами компиляторов, а итоги их тестов с разным охватом должны оставаться раздельными.

## Обеспечение инспектируемости передачи

Для разработчика, применяющего этот подход, полезный пакет передачи состоит из принятой ревизии, команд сборки, контрактов интерфейсов, точного манифеста регрессии и известных исключений. Это практическая рекомендация, выведенная из публичной архитектуры и тестовых сред, а не утверждение о том, что полный пакет такого вида был архивирован для эксперимента.

 Начните с небольшого изменения и сравните его промежуточные артефакты, диагностику и поведение исполняемого файла с этой ревизией. Раздел [Genesis development-history](/news/genesis-development-history) предоставляет соответствующий контекст для отслеживания вклада после того, как внесший его агент завершил работу.
