在對話、開發任務與 Git 變更之間切換，不應每次都重新建立專案上下文。Genesis PR #175 於 2026 年 11 月 20 日合入 `main`，引入包含專案導航、標籤頁、任務與對話歷史、Git 面板和就地設定的 LiveView 專案工作臺。相關工作區與草稿作用域更新，使所選專案成為可以貫穿這些介面的身份。[已合併的工作臺更新][pr]

![同一工作臺上的獨立專案抽屜分別儲存自己的筆記和工具](./cover.webp)

*概念插畫：每個專案保留自己的工作上下文。*

## 在同一處檢視專案

工作臺把導航和工作檢視連線起來。開發者可以返回專案，檢視任務或對話歷史，再檢查 Git 變更，而不必把每個檢視都當作新的起點。整合保留了上游工作區選擇器、賬戶設定和任務暫停、恢復流程，並在重連後恢復審批上下文。這些連續性改進建立在[此前的 Assistant 任務工作流][previous]之上，具體動作仍由結構化審批確定授權範圍。[工作臺整合][pr]

例如，開發者在一個庫與使用它的應用之間交替工作。開啟應用標籤頁時，為庫寫下的需求草稿應仍留在庫專案中。Git 操作也應指向所選專案的伺服器和倉庫。合入的變更會在工作臺執行 Git 操作前檢查專案歸屬；連線不可用時保留所選節點，不把操作轉到儀表盤所在主機。

## 草稿身份不只是路徑

共享的 `DraftScope` 用 `{node, token}` 定義瀏覽器草稿。已掛載到虛擬上下文樹的專案使用 `vct:///projects/<name>` 掛載點；尚未掛載的專案回退到作業系統絕對路徑。兩者同時存在時優先使用掛載點。因此，同一掛載專案的不同路徑寫法可以訪問同一份草稿，而同一路徑上的不同 VCT 掛載點仍各自獨立。[草稿作用域實現][scope]

瀏覽器儲存鍵由節點和這個令牌共同組成。後續修復會在專案的 VCT 掛載點就緒後接管原來按路徑儲存的草稿，處理從選擇目錄到登記專案的過渡。這是瀏覽器草稿的連續性，與任務持久化不同，也不意味著伺服器重啟後對話必然能夠恢復。[草稿接管修復][adopt]

遠端專案還需要原樣保留路徑：儀表盤不能按瀏覽器所在主機的檔案系統規則改寫它。提交恢復的草稿前，應確認所選節點、倉庫和模型，尤其是在本地與遠端專案之間切換之後。

## 工作區用於分組，任務仍需要真實目錄

VCT 新增了位於 `vct:///workspaces/<name>` 的工作區分組層。工作區包含有序成員列表和可選說明，成員引用專案掛載點或作業系統路徑；工作區不能巢狀。Projects 面板和 Assistant 選擇器能夠展示這些分組，只讀工作區 API 則讓 Assistant 檢視成員。[工作區操作介面][workspace]

分組本身沒有執行目錄。因此，對僅有工作區的選擇，`DraftScope.path/1` 不返回路徑，任務接納邏輯也拒絕把 VCT 掛載點當作任務路徑。在庫與應用的例子中，可以把兩者放入同一工作區，便於共同瀏覽；啟動開發任務前，再選擇實際接收任務的成員專案。工作區不會讓所有成員自動成為寫入目標。

在原始碼檢出目錄中，`mix vct.workspace list` 和 `mix vct.workspace show <name>` 用於檢查分組。文件中的 `create` 命令接受重複的 `--member` 引數和可選 `--data-dir`；應使用目標 Genesis 例項的資料目錄。檢查時會報告缺失成員，不會靜默丟棄。修改分組前請核對連結中的命令約定。

## 檢查檢視之間的交接

PR 記錄了建立並完成任務、Assistant 鍵盤提交與流式輸出、賬戶設定介面的瀏覽器檢查，也記錄了一次限定到專案的 Assistant 任務查詢超時。檢查長任務時，這一區別很實際：請求被接受與任務結果被觀測到，是兩個不同事件。[驗證記錄][pr]

在包含這些變更的構建中，可以嘗試為兩個專案分別保留草稿，重連所選節點，再開啟目標專案的 Git 面板。確認草稿回到正確專案，審批仍顯示真實執行目標。隨後跟蹤任務記錄中的狀態，而不是把標籤頁恢復視為後臺工作完成的證明。
