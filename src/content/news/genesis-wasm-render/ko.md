소프트웨어 WebGL 렌더러는 단순히 알아볼 수 있는 이미지를 그리는 것 이상의 역할을 수행해야 합니다. 셰이더를 컴파일하고, API 상태를 유지하며, 올바른 순서로 입력을 검증하고, 모듈 경계 전반에서 이미지 정밀도를 보존해야 합니다. Genesis WASM Render 사례에는 이러한 요구 사항을 디버깅하고 재점검한 두 가지 구체적인 예시가 포함되어 있습니다.

![와이어프레임 기하 구조가 셰이딩된 픽셀 이미지로 변환되는 과정](./software-graphics-pipeline.webp)

[Evidence record](https://genesis.evox.group/evidence/tbench-wasm/)에 따르면 DeepSeek V4 Flash로 개발된 TypeScript 구현체는 다음과 같은 지표를 기록했습니다. Khronos CTS 케이스 2,019개 중 2,017개 통과, 약 36달러의 모델 토큰 비용 발생, 첫 번째 에이전트 커밋과 마지막 커밋 사이의 간격 65.9시간. 이 시간 간격은 리포지토리의 히스토리 기간이며, 실제 에이전트의 가동 시간을 측정한 것은 아닙니다.

## 사용 가능한 인터페이스를 기준으로 파이프라인 분할

[source architecture](https://github.com/BillHuang2001/tbench-wasm/blob/67f620392b667714ba028f320d0e24f8ed32a16a/src/CONTEXT.md)는 셰이더 컴파일 및 링크, 래스터화, WebGL 상태 및 객체, 그리고 프리젠테이션/이미지 디코딩을 분리합니다. 셰이더 결과물은 가시적인 이미지가 되기 전까지 보간(interpolation), 프래그먼트 실행, 텍스처 처리 및 드로잉 버퍼를 거쳐야 합니다.

런타임 의존성이 전혀 없는 이 렌더러는 네이티브 GPU 렌더링 없이 실행되는 것을 목표로 합니다. 다만 이를 테스트하기 위해 브라우저 기반의 적합성 테스트 도구(conformance harnesses)가 여전히 사용되며, 이러한 검증 환경은 렌더러의 런타임 의존성 없음 선언과는 별개의 사안입니다.

## 텍스처 바인딩 오류 이전에 발생해야 했던 보안 오류

실패한 WebGL2 페이지 중 하나는 출처가 오염된(origin-tainted) 이미지 소스와 관련이 있었습니다. [final verification record](https://github.com/BillHuang2001/tbench-wasm/blob/67f620392b667714ba028f320d0e24f8ed32a16a/tests/conformance/FINAL.md#vs-previous-record-bundle-e3565d4-2015p4f)에 따르면, 이는 워커 기능의 부재가 아니라 검증 순서의 문제로 추적되었습니다.

기존 구현에서는 소스의 출처가 깨끗한지(origin-clean) 확인하기 전에 텍스처 바인딩을 먼저 확인했습니다. 수정 사항 `7d8718a`는 이미지 및 서브 이미지 업로드를 모두 포함하는 6개의 관련 이미지 소스 엔트리 포인트 전체에서 보안 확인을 바인딩 검증보다 앞으로 이동시켰습니다. 그 결과 해당 페이지의 테스트 결과는 **9개 통과 / 4개 실패에서 13개 통과 / 0개 실패**로 변경되었습니다.

이는 통합의 문제입니다. 두 검증 로직은 모두 존재했으나, 그 순서가 관찰 가능한 API 동작을 변화시킨 것입니다. 수정된 결과는 단순히 해당 동작만 확인하는 것에 그치지 않고 전체 스위트 실행에 포함되어 다른 동작에 영향이 없음을 검증받았습니다.

## 렌더러에 도달하기 전 실패한 높은 비트 심도 텍스처

두 번째 페이지는 더 높은 정밀도의 텍스처 입력을 테스트했습니다. 동일한 기록에 따르면 이미지 디코딩 경로에서 업로드 전 소스를 채널당 8비트로 축소하고 있었습니다. 수정 사항 `89e4559` 및 `9bd7811`을 통해 JavaScript 16비트 PNG 경로를 추가하고 RGBA 입력을 포함한 채널 처리를 수정했습니다.

`tex-image-10bpc` 페이지는 **2개 통과 / 1개 실패에서 3개 통과 / 0개 실패**로 개선되었습니다. 관련 구현은 [presentation-layer PNG decoder](https://github.com/BillHuang2001/tbench-wasm/blob/67f620392b667714ba028f320d0e24f8ed32a16a/src/present/png.ts)에 있습니다. 이 사례는 왜 셰이더 연산만 변경해서는 모든 정밀도 실패를 해결할 수 없는지 보여줍니다. 데이터가 상위 단계에서 이미 정밀도를 잃었기 때문입니다.

## 실행된 렌더러를 포함한 제출 번들 검증

[August 29 final record](https://github.com/BillHuang2001/tbench-wasm/blob/67f620392b667714ba028f320d0e24f8ed32a16a/tests/conformance/FINAL.md)는 번들 커밋 `c4ffbff`를 식별합니다. 기록에 따르면 체크인된 `renderer.js`는 검증을 위해 다시 빌드하지 않고 체크아웃된 상태 그대로 테스트되었습니다.

| 평가된 스위트 | 통과 | 실패 | 타임아웃 / 오류 |
| --- | --- | --- | --- |
| WebGL1 | 833/835 | 2 | 0 / 0 |
| WebGL2 | 1,184/1,184 | 0 | 0 / 0 |
| Combined | 2,017/2,019 | 2 | 0 / 0 |

분모는 해당 테스트 트리의 매니페스트를 따릅니다. 또한 기록에 따르면 점수가 매겨진 2,019개 페이지 모두에서 소프트웨어 렌더러가 활성화된 것으로 보고되었으므로, 네이티브 폴백(fallback)이 통과 결과를 만들어낸 것이 아님을 확인했습니다. 수정된 두 WebGL2 페이지의 경우, 전체 실행을 통해 이전의 통과 페이지들을 유지하면서 실패했던 부분들을 복구했습니다.

![문서화된 Genesis 실행에 대한 WebGL 적합성 결과](./wasm-render-results-en.png)

*과거 결과 수치이며, 버전 관리되는 최종 기록이 평가된 매니페스트와 개수를 정의합니다.*

## 대조군을 통한 잔여 실패 조사

두 개의 WebGL1 페이지는 여전히 실패 상태로 남았습니다. 최종 기록은 낮은 알파 값 컬러 케이스의 원인을 Chromium의 2D 캔버스 프리젠테이션/리드백(readback) 동작으로 돌렸으며, 네이티브 WebGL에서도 동일한 실패가 발생한다고 보고했습니다. 이중 밑줄(double-underscore) 셰이더 식별자의 경우에도 네이티브 Chrome에서 해당 테스트 페이지가 실패했음을 보고했습니다.

이것은 프로젝트의 문서화된 대조 결과이며, 독립적인 재현 결과는 아닙니다. 이는 2,017/2,019라는 수치를 무조건적인 호환성 주장으로 바꾸지 않으면서도, 잔여 실패에 대한 저자들의 분류 근거를 설명해 줍니다.

시각적 비교는 별도의 체크 사항입니다. Evidence record에 따르면 엄격한 **0.1% 픽셀 임계값에서 three.js 페이지 38개 중 16개**, **Babylon.js 씬 16개 중 13개**가 일치하는 것으로 보고되었으며, 이는 선택된 하위 집합에 대한 결과입니다. API 적합성과 픽셀 일치도는 서로 다른 속성을 측정하며, 높은 CTS 통과 횟수가 시각적 실패를 상쇄하는 것은 아닙니다.

## 테스트 페이지에서 최종 결과물까지의 실패 추적

필요한 테스트 트리와 도구 의존성이 준비된 상태에서, 최종 기록은 다음과 같은 WebGL2 엔트리 포인트를 문서화합니다.

```bash
npx tsx tests/conformance/run.ts --renderer ./renderer.js --suite webgl2 --report tests/reports/webgl2-FINAL2.json
```

기록에 따르면 상세한 JSON 출력물은 gitignore 처리되어 있습니다. 체크인된 보고서와 수정 식별자가 공개적인 추적 경로입니다. 본 기사에서는 해당 스위트를 재실행하지 않았습니다.

아카이브의 135,165개 텍스트 라인에는 생성된 번들, 외부 라이브러리, 락파일 및 문서가 포함되어 있습니다. 36달러의 비용은 하드웨어를 제외한 모델 토큰 비용입니다. 이 사례를 조사할 때는 검증 순서 수정 사항과 해당 테스트 페이지부터 시작하십시오. 이는 코드의 양에만 의존하지 않고 특정 실패, 소스 변경, 그리고 통합된 결과 사이의 연결 고리를 보여줍니다.
