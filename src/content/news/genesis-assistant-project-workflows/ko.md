프로젝트 수정을 요청하려면 대상, 승인된 작업, 결과를 추적할 방법이 필요합니다. 2026년 11월 15일 `main`에 병합된 PR #172는 Genesis Assistant에서 이 단계를 연결하며, [대화의 연속성][previous]을 프로젝트 작업으로 확장합니다.

![승인대를 거쳐 별도 작업대로 이동하는 프로젝트 요청](./genesis-assistant-project-workflows.webp)

*개념 일러스트: 범위가 지정된 요청이 승인 후 백그라운드 작업이 됩니다.*

## 먼저 대상 선택

일반 대화와 작업 제어에는 Genesis 체크아웃이 필요 없고, 소스 참조는 승인받는 선택 기능입니다. 선택 호스트의 프로젝트는 생략된 작업 경로를 채우지만 파일을 읽거나 개발을 허가하지 않습니다. 답변 중에는 프로젝트 전환이 잠기며, 다른 경로를 명시하면 승인 화면에 실제 대상으로 표시합니다. Assistant는 MCP와 열한 가지 작업 제어 정의를 공유하고, 변경 승인을 정확한 구조화 매개변수와 서버가 관리하는 노드·대화 식별에 연결합니다. [병합된 변경][workflows]

선택은 노드와 대화에 속하며 같은 노드의 새 대화가 이를 이어받을 수 있습니다. 서버가 도구에 노드와 대화의 식별 정보를 제공하므로 모델이 임의로 만들지 않습니다. 요청에서 다른 경로를 명시하면 승인 화면에는 그 실제 대상이 표시되어야 합니다. 이름이 비슷한 저장소 두 개를 다룰 때 시작 전에 경로를 확인하면 잘못된 프로젝트의 작업을 승인하는 일을 피할 수 있습니다.

## 승인에서 작업 추적으로

MCP와 공유하는 열한 가지 정의는 조회와 변경을 구분합니다. 작업 상태 읽기는 바로 실행하지만 시작, 취소, 요구사항 전송에는 변경할 수 없는 구조화된 매개변수에 연결된 승인이 필요합니다. 거절되거나 시간이 초과되면 작업을 실행하지 않습니다. 테스트를 수정하려면 실패 맥락을 제공하고 제안된 대상과 매개변수를 검토한 뒤 그 요청을 승인합니다. 시작 후에는 접수 메시지만으로 성공을 판단하지 말고 작업 추적과 결과 검토를 엽니다.[도구 및 승인 계약][workflowguide]

시작에 성공하면 자동으로 추적하며, 검색 가능한 Tasks 선택기에서 기존 작업을 연결할 수도 있습니다.

## 답변과 작업 구분

추가 요구사항을 보내면 대기열에 들어갈 뿐, 작업 중인 개발자가 이미 반영했다는 뜻은 아닙니다. 마찬가지로 **Stop reply**는 실행 중인 도구 묶음이 끝난 뒤 응답을 멈추고 세션을 유지하며 개발 작업은 계속됩니다. 카드는 관측한 상태, 개수, 갱신 시각을 표시하며 진행률을 만들어내지 않습니다. 갱신에 실패하면 마지막 관측을 유지합니다. 이를 통해 기다리기, 결과 확인, 요청 구체화, 취소 요청 중 무엇이 필요한지 판단할 수 있습니다. 취소는 Git 변경을 되돌리지 않습니다.

세션 종료 후 작업 연결은 남지만 메모리 대화는 서버 재시작 후 복원되지 않습니다. 영속 작업은 다시 찾아 추적할 수 있습니다. PR #172가 포함된 빌드에서 시도하고, 제출 결과가 불확실하면 재시도 전에 상태를 확인하세요. [업데이트된 가이드][workflowguide]

## 올바른 파일 전달

브라우저 업로드는 텍스트, PDF, DOCX, 이미지, 오디오를 메시지당 네 파일, 파일당 15 MiB까지 지원하며 완료된 첨부는 본문 없이 보낼 수 있습니다. 보조 서버 경로 입력은 대시보드 로컬 노드를 지원하며 미지원 원격 노드를 해당 호스트로 대체하지 않습니다.

브라우저 업로드는 현재 사용 중인 기기에서 파일을 가져옵니다. 서버 경로는 다른 위치를 가리키며 대시보드의 로컬 노드에서만 지원됩니다. 대화나 노드를 바꾸면 대기 중인 전송이 취소되므로 맥락을 바꾸기 전에 업로드 완료를 기다립니다. Genesis 코드를 참조하려는 경우 선택적인 소스 참조 준비에는 여전히 승인이 필요하며 그 버전을 실행 중인 런타임과 비교해야 합니다. 프로젝트 맥락과 Genesis 소스 참조는 서로 다른 역할을 합니다.[파일 및 소스 참조][workflowguide]
