Агент разработки может уже знать цель и путь проекта. Передавая исполнение другому движку, ему нужно из той же беседы запустить работу, следить за ней и получить результат. 11 ноября 2026 года в ветку `main` Genesis вошла локальная точка доступа Model Context Protocol (MCP). Совместимые агенты получают доступ к существующим API задач через одно подключение. [Изменение в основной ветке][pr]

## Подключение к процессу Genesis, который выполняет задачу

Точка доступа Streamable HTTP `/mcp` работает на запущенном сервере Genesis. Сервер проверяет подлинность запроса и его аргументы, затем вызывает существующий API задач или планировщика. Работа на сервере продолжается после завершения HTTP-запроса. Соединение не хранит состояния, поэтому для последующего поиска нужно сохранить ID задачи.

Genesis принимает соединения через loopback и проверяет Host и Origin. Запросы используют bearer-токен из файла `mcp-token` запущенного экземпляра. Среда агента должна поддерживать Streamable HTTP и постоянное хранение заголовка авторизации. Genesis и доступный для записи каталог проекта должны находиться на одном компьютере. [Руководство по подключению][guide] описывает настройку сборки из исходников с этим изменением. Настройку выпущенной версии сервера см. в [Genesis 0.14.1][related].

## Цель с достаточным контекстом

Предположим, агент нашёл дефект в парсере и должен делегировать регрессионный тест. Сначала он может проверить локальную настройку с помощью `genesis_check`, затем передать в `genesis_start_task` абсолютный путь к основной рабочей копии и цель с проблемным входом, ожидаемым поведением и способом проверки. Genesis использует собственную настроенную модель. Поэтому существенный контекст из беседы вызывающего агента нужно включить в цель.

Девять инструментов охватывают проверку готовности, перезагрузку конфигурации, поиск моделей, отправку и список задач, состояние, результаты, сообщения и отмену. Существующему Git-репозиторию нужен первый коммит. Эта точка входа ожидает основную копию с каталогом `.git` и отклоняет связанные рабочие деревья и корни подмодулей. [Требования к задачам и репозиториям][guide]

## Поиск задачи по ID после переподключения

Сохраните ID, полученный при отправке. После переподключения вызовите `genesis_get_task` с этим ID либо просмотрите недавние задачи проекта, прежде чем повторно отправлять запрос. Статус включает ограниченный набор данных о ходе работы из планировщика и сохранённого состояния. При опросе можно исключить полный результат и использовать маркер изменения, чтобы ждать обновления ограниченное время.

Ответ на сообщение подтверждает его постановку в очередь. Ответ на отмену показывает принятый запрос и сохранённое состояние. Для проверки результата прочитайте конечный статус, получите сохранённый результат через `genesis_get_result` и проверьте указанные коммиты и сведения о тестах. [Наблюдение и управление задачами][guide]

## Проверка подключения перед делегированием

Соберите подходящую ревизию и настройте провайдера в экземпляре Genesis, который будет выполнять работу. По руководству создайте закрытый токен и зарегистрируйте фактический loopback-адрес экземпляра в клиенте. Затем откройте новый сеанс клиента и вызовите `genesis_check`. Так можно отдельно проверить подключение MCP и готовность модели перед отправкой задачи. [Настройка и проверка соединения][guide]
