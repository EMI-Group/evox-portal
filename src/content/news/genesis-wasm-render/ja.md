ソフトウェアWebGLレンダラーは、単に認識可能な画像を描画する以上のことが求められます。シェーダーのコンパイル、API状態の維持、適切な順序での入力バリデーション、そしてモジュール境界を越えた画像精度の保持が必要です。Genesis WASM Renderの事例には、これらの要件がデバッグされ、再確認された2つの具体的な例が含まれています。

![ワイヤーフレームのジオメトリがシェーディングされたピクセル画像になる様子](./software-graphics-pipeline.webp)

[Evidence record](https://genesis.evox.group/evidence/tbench-wasm/)には、DeepSeek V4 Flashで開発されたTypeScript実装の記録が記されています。Khronos CTSの2,019ケース中2,017ケースに合格し、モデルトークンの費用は約36米ドル、最初と最後のエージェントコミットの間隔は65.9時間でした。この間隔はリポジトリの履歴期間であり、測定されたアクティブなエージェントの実行時間ではありません。

## 利用可能なインターフェースに沿ったパイプラインの分割

[source architecture](https://github.com/BillHuang2001/tbench-wasm/blob/67f620392b667714ba028f320d0e24f8ed32a16a/src/CONTEXT.md)では、シェーダーのコンパイルとリンク、ラスタライズ、WebGLの状態とオブジェクト、およびプレゼンテーション/画像デコードが分離されています。シェーダーの結果は、可視画像になる前に、補間、フラグメント実行、テクスチャ処理、および描画バッファを通過する必要があります。

実行時依存関係ゼロのこのレンダラーは、ネイティブGPUレンダリングを使用しない実行をターゲットとしています。テストには依然としてブラウザベースのコンフォーマンスハーネスが使用されていますが、その検証環境はレンダラーの実行時依存関係の主張とは区別されます。

## テクスチャバインドエラーの前にセキュリティエラーが発生する必要があった

失敗していたWebGL2のページの一つは、オリジンが汚染された（origin-tainted）画像ソースに関するものでした。[final verification record](https://github.com/BillHuang2001/tbench-wasm/blob/67f620392b667714ba028f320d0e24f8ed32a16a/tests/conformance/FINAL.md#vs-previous-record-bundle-e3565d4-2015p4f)によれば、これはワーカーの機能不足ではなく、バリデーションの順序に起因していました。

実装では、ソースがオリジンクリーンであるかどうかを確認する前に、テクスチャのバインドを確認していました。修正 `7d8718a` では、画像およびサブ画像のアップロードの両方をカバーする、関連する6つすべての画像ソースエントリポイントにおいて、セキュリティチェックをバインドバリデーションの前に移動しました。影響を受けたページは、**合格9 / 失敗4のサブテストから、13 / 0**へと変化しました。

これは統合の問題です。両方のチェックは存在していましたが、その順序が観察可能なAPIの挙動を変えていました。ターゲットとされた結果は、無関係な挙動が変化していないことの証明としてではなく、フルスイートの実行に含まれる形で確認されました。

## 高ビット深度テクスチャがレンダラーに到達する前に失敗していた

2つ目のページは、より高精度なテクスチャ入力をテストするものでした。同記録では、アップロード前にソースをチャンネルあたり8ビットに削減していた画像デコードパスが特定されました。修正 `89e4559` および `9bd7811` により、JavaScriptによる16ビットPNGパスが追加され、RGBA入力を含むチャンネル処理が修正されました。

`tex-image-10bpc` ページは、**合格2 / 失敗1のサブテストから、3 / 0**へと移行しました。関連する実装は、[presentation-layer PNG decoder](https://github.com/BillHuang2001/tbench-wasm/blob/67f620392b667714ba028f320d0e24f8ed32a16a/src/present/png.ts)です。この例は、シェーダーの演算を変更するだけではすべての精度の失敗に対処できなかった理由を示しています。データはすでに上流で精度を失っていたのです。

## 実行されたレンダラーを含む、提出されたバンドルの検証

[August 29 final record](https://github.com/BillHuang2001/tbench-wasm/blob/67f620392b667714ba028f320d0e24f8ed32a16a/tests/conformance/FINAL.md)は、バンドルのコミット `c4ffbff` を特定しています。チェックインされた `renderer.js` は、検証のために再ビルドされることなく、チェックアウトされた状態のままテストされたと記されています。

| 評価されたスイート | 合格 | 失敗 | タイムアウト / エラー |
| --- | --- | --- | --- |
| WebGL1 | 833/835 | 2 | 0 / 0 |
| WebGL2 | 1,184/1,184 | 0 | 0 / 0 |
| 合計 | 2,017/2,019 | 2 | 0 / 0 |

分母はそのテストツリーのマニフェストに従っています。また、採点された2,019ページすべてにおいてソフトウェアレンダラーがアクティブであったことが報告されており、ネイティブへのフォールバックが合格結果をもたらしたわけではないことが示されています。修正されたこれら2つのWebGL2ページについては、フル実行によって以前の合格ページを維持しつつ、両方の失敗が解消されました。

## 対照群を用いた残留失敗の調査

2つのWebGL1ページが失敗したまま残りました。最終記録では、低アルファカラーのケースについてはChromiumの2Dキャンバスのプレゼンテーション/リードバックの挙動に起因するとし、ネイティブWebGLでも同様の失敗が発生することを報告しています。ダブルアンダースコアのシェーダー識別子については、ネイティブのChromeでもテストページが失敗したと報告されています。

これらはプロジェクトで文書化された対照実験の結果であり、独立した再現ではありません。これらは、2,017/2,019という数字を無条件の互換性の主張に変えることなく、残留した失敗に対する作成者の分類を説明するものです。

視覚的な比較は別のチェック項目です。Evidence recordでは、選択されたサブセットにおいて、**厳格な0.1%のピクセル閾値でthree.jsの38ページ中16ページ**、**Babylon.jsのシーンでは16中13**が一致したと報告されています。APIコンフォーマンスとピクセルの一致は異なる特性を測定するものであり、高いCTS合格数は視覚的な失敗を打ち消すものではありません。

## テストページから最終成果物までの失敗を追跡する

必要なテストツリーとハーネスの依存関係が準備された状態で、最終記録はこのWebGL2エントリポイントを文書化しています。

```bash
npx tsx tests/conformance/run.ts --renderer ./renderer.js --suite webgl2 --report tests/reports/webgl2-FINAL2.json
```

記録では、詳細なJSON出力はgitignored（Git管理対象外）であると注記されています。チェックインされたレポートと修正の識別子が公開されている追跡記録であり、本記事においてスイートの再実行は行っていません。

アーカイブの135,165行の追跡テキスト行には、生成されたバンドル、ベンダー提供資料、ロックファイル、およびドキュメントが含まれています。36米ドルはモデルトークンをカバーしており、ハードウェア費用は含まれません。この事例を調査する際は、バリデーション順序の修正とそのテストページから始めてください。それは、コードの量だけに頼ることなく、特定の失敗、ソースの変更、および統合された結果を結びつけるものです。
