搜索程序时，编译本身就是实验预算的一部分。如果每一代都花很久准备计算图，仅加快设备执行只能解决部分问题。2026 年 10 月 30 日发布的 [EvoX Compiler v0.1.1][s1] 改进了准备路径，并修复后端故障场景。[包含 45 次提交的变更集][s2] 延续了 v0.1.0 的显式计算图流水线。

![不同程序结构被整理成紧凑的并行分组](./cover.webp)

*概念插画：在编译前组织一个程序种群。*

## 程序分组需要成本模型

种群变换 `batch_functions` 将兼容的候选程序组合为一张图。v0.1.1 在内部类别图中传播行依赖，并扩展 `bands="auto"` 使用的几何分组搜索。这有助于变换判断哪些计算依赖具体种群成员，以及应如何组织候选程序。

在遗传编程实验中，候选程序可能具有相同输入规格，却包含不同运算。单一扁平分组不一定最省计算。分组提供另一种组织方式，自动策略通过成本模型比较方案。关键仍是语义检查：合并结果第 i 行应与单独运行候选程序 i 一致。此次发布同步更新了相关回归测试。

## 消除计算图准备中的重复工作

多项改进针对设备运行前的 CPU 工作：通过直接遍历栈帧捕获源码位置，移除降级阶段重复的验证，并在 IR 验证中使用线性使用关系追踪及结果类型推断缓存。StableHLO 导出还增加了常量文本批量输出、类型文本缓存和表驱动运算分派。

这些改进位于不同阶段。导出加快不等于 GPU 内核本身更快。比较版本时，应分别测量追踪、变换、降级、编译和稳态执行。包含大量常量的大种群，与数值内核昂贵的小图，可能受不同成本主导。

## 后端故障更容易定位

IREE 适配器现在把单次分派的 HAL 绑定数量限制报告为可采取行动的 `BackendError`，帮助区分后端资源限制和数值程序错误。XLA 适配器则不再跨越 `PJRT_Client_Create` 持有共享客户端锁，修复同线程终结器导致的死锁，并增加回归测试。

后端支持仍以版本化支持矩阵为准。NumPy 提供 CPU 解释器；IREE、XLA 和 TVM 的依赖与设备要求不同，因此可以先用解释器结果建立参考，再检查编译路径。[版本 README][s3] 说明了这些边界及显式设备传输模型。

## 围绕一个代表性种群升级

基础包可使用 `pip install evoxc==0.1.1`；IREE 环境可使用 `pip install "evoxc[iree]==0.1.1"`。需要 Python 3.11 或更新版本。独立发行包 `evoxc-hf` 有自己的版本和升级周期；应保留原实验所用的后端插件配置。

从保存的种群和固定输入开始，将合并输出与逐个程序的参考运行比较，再分别测量准备和执行时间。若加速器报告绑定错误，保留计算图及后端信息用于诊断，不要悄悄改变实验。[v0.1.0 介绍][related] 解释整体流水线；v0.1.1 则让准备阶段和后端边界更便于实际使用。
