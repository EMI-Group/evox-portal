構建張量圖編譯器意味著要保持同一計算的多種實現之間的一致性。圖轉換可能會改變張量佈局；介面卡可能會拒絕某項操作；裝置呼叫可能會在計算完成前返回。EvoX Compiler 的公開原始碼把這些問題拆成了可檢查的介面與測試，也讓 Genesis 的開發成果有了更具體的觀察入口。

![用迴歸測試核對編譯器計算圖](./compiler-contract-layers.webp)

[10 月 28 日的 Evidence 快照](https://genesis.evox.group/evidence/evoxc/)記錄了 6,789 項測試透過，以及約 50 美元的模型 token 費用。為了分析這些數字背後的工程設計，本文還參考了公開可用的 v0.1.0 原始碼。快照和釋出版本的測試總數有所不同；下文中的實現示例均按其版本進行了標識。

## 將目標轉化為可測試的介面

EvoX Compiler 負責張量語言、EvoXIR 圖以及分階段執行介面。外部編譯器接收其匯出的表示，並處理最佳化、排程和程式碼生成。其[包契約](https://github.com/EMI-Group/evoxc/blob/v0.1.0/CONTEXT.md)記錄了依賴方向：值型別和 IR 支撐追蹤與運算元實現，圖變換和後端介面卡再建立在這些基礎之上。獨立的 `evoxc_hf` 包呼叫公開的編譯器 API；編譯器本身不匯入模型整合部分。

這種劃分給每項區域性開發任務設定了具體邊界。例如，轉換操作會生成另一個普通圖，而不是要求每個後端都理解 Python 的 `vmap`。後端尚不支援的情況必須透過明確的錯誤報告，而不是靜默地改變執行路徑。包級上下文文件記錄了另一個開發任務必須遵守的 API 和約束。

公開的流水線為 `trace → lower → compile → load → run`。每個階段都會返回一個獨立的物件。[規範測試](https://github.com/EMI-Group/evoxc/blob/v0.1.0/tests/test_spec_compliance.py)會檢查傳給錯誤階段的輸入，並拒絕把圖定義當作即時執行函式直接呼叫，並驗證便捷函式是否展開為文件記錄的流水線。測試還會拒絕從閉包中捕獲具體張量，除非作者顯式地嵌入它。這樣做在實踐中的好處是，看似方便的快捷方式不會悄悄引入第二套語義。

根據 Evidence 記錄，開發工作是逐層推進的，在繼續下一層之前必須透過 pytest 檢查。該倉庫為這種方法提供了可檢查的契約和測試；它不提供完整的智慧體決策存檔序列。

## 針對兩個參考標準檢查種群轉換

一個要求很高的特性是 `batch_functions`：將具有匹配輸入/輸出簽名的多個程式合併為一個圖。它的契約比“合併後的圖能執行”更強：輸出的第 i 行必須仍然等於程式 i 的結果。

[v0.1.0 整合測試](https://github.com/EMI-Group/evoxc/blob/v0.1.0/tests/transforms/test_batch_functions_integration.py)採用了一個簡短、易讀的示例。在相同的圖位置，三個程式分別執行 `x + 1`、`x * 2` 和 `x - 3`。當 `switch_ops=True` 時，合併後的圖透過逐行選擇來表示不同的操作。測試透過 IREE 的 CPU 路徑編譯該圖，並將其輸出與合併圖的 NumPy 執行結果以及原始函式的堆疊 NumPy 結果進行對比，誤差容限設為 `rtol=atol=1e-5`。

不依賴外部編譯器的檢查會確認 StableHLO 輸出中是否存在預期的選擇操作。另一個檢查則合併相同的程式並將其結果與 `vmap` 進行對比，在這種情況下不應需要選擇操作。這些測試共同檢查計算語義是否保持、匯出是否正確、後端是否能夠整合，而不是僅將成功編譯作為唯一的驗收條件。

## 裝置放置是正確性的一部分

GPU 可執行物件接收的資料，必須真實位於相應裝置上；給主機資料換一個裝置標籤不能替代傳輸。[張量與放置規範測試](https://github.com/EMI-Group/evoxc/blob/v0.1.0/tests/test_spec_compliance.py)會檢查資料的真實存放位置，傳輸是否透過 `Tensor.to(device)` 顯式進行，以及無效的放置是否會觸發 `DeviceError`。

這對效能測量也至關重要。如果每次呼叫都重新傳輸模型權重，那麼延遲資料測量的任務負載就與保持權重駐留的任務負載完全不同。[v0.1.0 模型整合文件](https://github.com/EMI-Group/evoxc/blob/v0.1.0/evoxc_hf/CONTEXT.md)將模型檢查點載入、前向計算和可執行物件的分階段構建分開。引數保持為顯式的圖輸入，使其放置位置清晰可見。

## 返回的呼叫並不一定意味著工作已完成

XLA 的裝置常駐執行路徑可以先提交任務，再在計算完成前返回。因此，如果僅對 `run` 計時，會低估執行時間。[同步測試](https://github.com/EMI-Group/evoxc/blob/v0.1.0/tests/backends/test_xla_synchronize.py)檢查事件生命週期：執行會累積完成控制代碼；`synchronize()` 等待並銷燬它們；再次同步時不會重複呼叫外掛處理已完成的事件。

錯誤情況也同樣具體。如果等待失敗，剩餘的控制代碼仍必須被處理，並丟擲第一個錯誤。不提供完成事件的外掛必須觸發顯式錯誤，而不是虛假的完成宣告。

這些測試使用了一個不進行數值計算的小型偽 PJRT 外掛。它們驗證的是同步語義和清理工作，而不是 GPU 吞吐量或數值精度。這種區分使測試的證據與宣告相匹配。

來源：[Evidence 驗證](https://genesis.evox.group/evidence/evoxc/#verification) 和 [版本化釋出狀態](https://github.com/EMI-Group/evoxc/blob/v0.1.0/README.md#status--deferrals)。這些是專案報告的執行結果。部分測試會依據依賴項和硬體條件跳過，因此仍有未執行的路徑；透過 CPU 測試並不代表對每種加速器都進行了驗證。

Evidence 快照追蹤的 285,659 行文字包括測試、文件和基準測試材料。其約 50 美元的費用涵蓋了模型 token，不包括硬體；模型、執行回合數和實際執行時長未報告。倉庫的時間跨度並非連續的自主執行時間。

該倉庫將程式碼、測試和文件的生成歸功於 Genesis。具體成果是一個具有可獨立檢查的階段契約、計算語義保持測試和裝置完成語義的編譯器。可以從[種群整合測試](https://github.com/EMI-Group/evoxc/blob/v0.1.0/tests/transforms/test_batch_functions_integration.py)開始，追蹤一個特性如何跨越這些邊界；[EvoX Compiler 概覽](/news/evox-compiler)解釋了面向使用者的流水線。
