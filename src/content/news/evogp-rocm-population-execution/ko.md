빠른 유전 프로그래밍 커널만으로는 충분하지 않습니다. 사용 가능한 GPU가 지원되어야 하고 진행 보고가 매 세대 비용을 지배하지 않아야 합니다. EvoGP의 [2026년 10월 16일 병합][s1]은 표준 파이프라인의 Python 적합도 축약을 바꿉니다. 앞서 [6월 17일 병합한 AMD ROCm 지원][s2]과 함께 같은 트리 탐색 구현의 활용 범위를 넓힙니다.

![서로 다른 가속기 보드 위의 동일한 프로그램 트리](./cover.webp)

*개념 삽화: 같은 프로그램 표현이 GPU 백엔드 경계를 넘습니다.*

## 통계는 텐서 연산으로 처리

적합도 텐서의 Python 내장 최댓값·최솟값을 `torch.max`, `torch.min`으로 교체합니다. 큰 장치 텐서를 Python으로 순회하면 언어 경계 작업이 늘지만 텐서 축약은 수치 프레임워크 내부에서 처리합니다. 적합도 평가가 저렴한 경우 특히 중요합니다.

대규모 기호 회귀에서 표현식 평가는 병렬이어도 세대별 극값 출력은 비쌀 수 있습니다. 수정은 통계의 의미를 유지하면서 이 불균형을 줄입니다. PR은 백만 개체 예제의 큰 개선을 보고하지만 완전한 벤치마크 절차는 없습니다. 실제로는 보고 비용을 포함한 세대 전체를 프로파일링해야 합니다.

## CUDA와 ROCm의 공통 소스

6월 통합은 PyTorch의 빌드 시 HIP 변환으로 CUDA 확장 소스를 AMD용으로 컴파일합니다. 백엔드별 옵션을 선택하고 CUDA 전용 헤더를 보호해 HIP 빌드가 깨지지 않게 합니다. ROCm PyTorch로 별도 알고리즘 구현 없이 확장을 만들 수 있습니다.

트리 인터프리터의 동적 장치 스택 할당도 고정 크기 로컬 배열로 바뀝니다. 기여자는 AMD 오류를 동시에 상주한 wavefront 간 할당 별칭 문제로 추적했습니다. 다른 스레드의 임시 상태를 쓰면 적합도와 후속 선택이 잘못되므로 스레드별 스택 분리는 중요합니다.

## 백엔드에 맞는 빌드 환경

[소스 설치 지침][s3]은 적합한 GPU 도구, C++ 컴파일러, 호환 PyTorch를 요구합니다. AMD에서는 `hipcc`가 포함된 ROCm과 ROCm PyTorch를 사용하고 `--no-build-isolation`으로 설치된 PyTorch 환경에서 확장을 빌드합니다.

ROCm에서도 예제는 `cuda` 장치 문자열을 유지합니다. 이것이 PyTorch 인터페이스입니다. 특정 AMD 아키텍처는 `PYTORCH_ROCM_ARCH`로 선택합니다. 이는 빌드 설정이며 트리 표현이나 진화 연산자를 다시 작성할 필요는 없습니다.

## 작은 탐색을 확인한 뒤 확대

기여자는 MI250X, W7800, RX 9070 XT, PRO V710에서 기호 회귀를 검증했다고 보고하며 PR에 OS와 ROCm 버전을 명시합니다. 1,000개체, 100세대, 고정 시드를 사용한 해당 구성의 보고 결과이지 하드웨어 전반의 성능 보장은 아닙니다.

빌드 후 `python -m evogp.sr_test`로 유한한 적합도와 정상 종료를 확인합니다. 이후 입력, 시드, 개체 수를 고정하고 보고를 켠 실행과 끈 실행을 비교해 평가기와 관리 비용을 나눕니다. [EvoGP 연구 소개][related]는 텐서화 트리를 설명하며, 두 변경은 그 표현을 실제 하드웨어의 탐색으로 연결합니다.
