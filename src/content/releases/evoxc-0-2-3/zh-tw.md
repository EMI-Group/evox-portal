EvoX Compiler v0.2.3 於 2026 年 11 月 25 日（UTC）釋出，提供 Python wheel 和原始碼歸檔。簡短的 GitHub 說明連結到 v0.2.2 至 v0.2.3 的差異；版本化變更日誌則記錄了通向本次分發的 0.2 系列主要變化與打包修復。對於從 0.1 升級的使用者，重點是安裝哪一對編譯器和執行時、如何選擇物理裝置，以及需要重新檢查哪些數值行為。[版本釋出][release] · [變更日誌][changes]

*概念插畫：可用的發行包需要與執行環境相匹配。*

## 讓編譯器與執行時保持配套

IREE 選用相依套件現在要求編譯器和執行時均為 3.13.0 至低於 3.14 的版本。編譯產物具有版本依賴性，不能假定另一組編譯器和執行時生成的檔案可以原樣載入。上游記錄重新驗證了 llvm-cpu，以及 AMD Instinct MI300X、ROCm 7.1 環境中的 ROCm/HIP，包括此前 IREE 版本失敗的迴圈和掃描。這些檢查並不自動涵蓋 CUDA、多 rank 執行或所有模型基準。[版本化依賴要求][requirements] · [變更日誌][changes]

介面卡也明確控制裝置到主機的結果回讀，不再直接依賴執行時的快捷路徑。這關係到程式計算正常、卻在取回結果時失敗的情況。主機記憶體可以保留對映路徑；裝置緩衝區需要顯式傳輸。評估應用工作負載時，應計入傳輸時間，並將其與核心執行時間分開。

## 先發現 XLA 外掛，再選對裝置

XLA 註冊不再在呼叫方提供路徑之前執行不帶選項的外掛探測。發現過程依次考慮顯式外掛選項、對應環境變數、已知位置及已安裝的 JAX 外掛包，而不匯入 JAX 本身。可用性檢查移至選項已經齊備的編譯和載入階段。構建輔助函式也會把解析後的選項傳給載入過程，修復編譯時找到外掛、載入時卻丟失配置的問題。[後端指南][guide]

ROCm 外掛必須服務於 ROCm 裝置，CUDA 外掛必須服務於 CUDA 裝置。提供 GPU 外掛卻保留預設 CPU 選擇會被拒絕。進行 GPU 實驗時，應選擇對應裝置，並顯式把張量移過去。把結果複製回主機之前，先檢查輸出所在裝置。XLA 執行失敗時也會清空快取的輸出指標槽，避免後續呼叫複用失效緩衝區指標。

## 比較速度之前，先複核語義

NumPy 參考直譯器使用快取的分派計劃，在最後一次使用後釋放不再需要的中間值，並共享不可變的主機裝置例項。這些變化減少準備和分配開銷，無需改變公開呼叫方式。變更日誌中的 TensorNEAT 測量針對特定工作負載，不能當作通用加速倍數。

編譯後的餘數運算現在遵循 NumPy floormod：結果符號與除數一致。因此，負數輸入適合作為升級檢查。保留固定輸入和參考輸出，再用適合資料型別的容差比較直譯器與編譯器結果。打包修復接受 maturin 附帶的共享庫目錄，並將經過測試的分發檔案平鋪到暫存目錄，解決阻止產物釋出的問題。[修復記錄][changes]

## 在乾淨環境中升級

需要 Python 3.11 或更新版本。使用 pip 安裝 release 資源中選定的 0.2.3 wheel；該版本提供 Linux、macOS 和 Windows wheel 和原始碼歸檔。IREE 選用相依套件可用 `pip install "evoxc[iree]==0.2.3"` 安裝，並確認 IREE 依賴成對匹配。獨立的 evoxc-hf 發行套件使用自己的版本號。執行 `pip check`，檢視已安裝版本，再複核一個代表性計算圖、一個負數餘數案例和一次裝置往返傳輸，然後遷移更大的工作負載。[安裝指南][guide]

有關這些後端周圍的計算圖變換、自訂運算子和明確的編譯階段，可搭配本版本文件閱讀[自訂編譯專題][related]。
