コーディングエージェントが目的とプロジェクトのパスを把握していても、別のエンジンに作業を任せるには、同じ会話から開始、追跡、結果の取得を行う手段が必要です。2026 年 11 月 11 日、Genesis の `main` にローカルの Model Context Protocol（MCP）エンドポイントがマージされました。対応するコーディングエージェントは、一つの接続から既存の Genesis タスク API を利用できます。[マージされた変更][pr]

![同じ作業台にある二つの端末がタスク票と対応する結果をやり取りする](./genesis-local-mcp.webp)

*コーディングエージェントと Genesis が同じマシン上で作業を引き継ぐ様子を描いたイラスト。*

## 作業を担当する Genesis プロセスに接続する

Streamable HTTP の `/mcp` は実行中の Genesis サーバーに組み込まれています。サーバーはクライアントのリクエストを認証し、引数を検査して既存のタスクまたはスケジューラー API を呼び出します。HTTP リクエストが終わっても、作業はサーバー上で続きます。接続はステートレスなので、あとで参照するにはタスク ID を保持します。

Genesis はループバック接続を受け付け、Host と Origin を検証します。リクエストには実行インスタンスの `mcp-token` ファイルにある bearer 資格情報を使います。エージェントのホストは Streamable HTTP と認証ヘッダーの永続化に対応している必要があります。Genesis と書き込み可能なプロジェクトディレクトリは同じマシンに置きます。[接続ガイド][guide]には変更を含むソースビルドの手順があり、リリース済みのサーバー設定は [Genesis 0.14.1][related] を参照できます。

## 作業に必要な背景を目的に含める

エージェントがパーサーの不具合を特定し、回帰テストを委任する場面を考えます。まず `genesis_check` でローカルの設定を確認し、`genesis_start_task` に主チェックアウトの絶対パスと、不具合を起こす入力、期待する動作、テスト方法を記した目的を渡します。Genesis は独自に設定されたモデルを使うため、呼び出し元の会話で得た関連情報は目的に含めます。

九つのツールは準備状況、設定の再読み込み、モデル一覧、タスクの送信・一覧・状態・結果、メッセージ、キャンセルを扱います。既存の Git リポジトリには最初のコミットが必要です。この入口では `.git` ディレクトリのある主チェックアウトを前提とするため、リンクされたワークツリーやサブモジュールのルートは受け付けません。[タスクとリポジトリの要件][guide]

## 再接続したらタスク ID で追跡する

送信時に返された ID を保存します。再接続後は、その ID で `genesis_get_task` を呼ぶか、プロジェクトの最近のタスクを調べてから再送を判断します。状態には、スケジューラーと保存済みタスク状態から得た範囲の限られた進捗が含まれます。ポーリング時に結果の全文を省き、変更トークンを使って一定時間だけ更新を待つこともできます。

メッセージの応答はキューへの受理を示し、キャンセルの応答は受理した要求と保存状態を示します。作業の結果は最終状態を確認し、`genesis_get_result` で保存済みの結果を取得して、報告されたコミットとテスト証拠を照合します。[タスクの観察と制御][guide]

## 委任の前に接続を確認する

対象リビジョンからビルドし、作業を行う Genesis インスタンスでプロバイダーを設定します。ガイドに沿って非公開の資格情報を作り、実際のループバックアドレスをクライアントに登録します。新しいクライアントセッションから `genesis_check` を実行すれば、MCP 接続とモデルの準備状況を別々に確認してからタスクを送信できます。[設定と接続の確認][guide]
