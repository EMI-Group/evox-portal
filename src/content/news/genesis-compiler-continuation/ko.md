[2026년 9월 7일 Evidence 기록](https://genesis.evox.group/evidence/compiler-continuation/)은 이전 에이전트의 대화 컨텍스트를 유지하지 않은 채, **GLM 5.2에서 DeepSeek V4 Flash**로의 컴파일러 핸드오프를 설명합니다. 승인된 소스 트리와 Git 계보는 그대로 유지되었습니다. 엔지니어링 측면의 핵심은 수신 모델이 무엇을 조사할 수 있으며, 이후의 변경 사항을 어떻게 평가할 수 있느냐는 것입니다.

![서로 다른 도구 세트 간에 유지되는 컴파일러 프로젝트](./compiler-model-handoff.webp)

해당 기록에 따르면, 연속성 작업 이후 **1,820/1,820개의 유지된 LLVM SingleSource 케이스가 통과**되었으며 작업 재귀 깊이는 4에서 8로 증가했습니다. 수정 사항별 트랜스크립트나 연속성 작업으로 추가된 코드 분량 및 비용은 공개되지 않았습니다. 아래의 공개 jcc 소스는 컴파일러의 인터페이스와 회귀 메커니즘을 설명하며, 해당 별도 스냅샷이 핸드오프 작업의 정확한 시퀀스를 재구성하지는 않습니다.

## 상속된 컴파일러에는 후속 모델이 보존해야 할 경계가 있습니다

[jcc 아키텍처](https://github.com/EMI-Group/genesis-demo-jcc/blob/a8c116ec7ed3d59479ad3be8fed3e63384f50a87/docs/architecture.md)는 프론트엔드, 타입이 지정된 CIR 중간 표현(intermediate representation), 최적화 도구, 기계어 백엔드, 어셈블러 및 커맨드 라인 드라이버를 분리합니다. 프론트엔드는 검증된 구문 트리를 로워링(lowering) 단계로 전달하며, 이후 단계에서는 원래 소스를 독립적으로 재해석하는 대신 결과로 나온 표현을 소비합니다.

이는 새로운 모델이 하나의 구성 요소를 변경할 때 중요하게 작용합니다. 로워링 단계의 산술 연산 수정은 여전히 CIR 타이핑을 만족해야 하며, 호출 규약(calling-convention) 변경은 레지스터 할당 및 객체 생성과 일치해야 합니다. 이는 아키텍처에 문서화된 의존성의 예시이며, 특정 핸드오프 복구 작업에 대한 주장이 아닙니다.

드라이버는 중간 중단 지점을 노출합니다. 전처리를 위한 `-E`, CIR을 위한 `-emit-jcc-ir`, 어셈블리를 위한 `-S`, 객체 생성을 위한 `-c`가 이에 해당합니다. 이러한 결과물들은 링크된 실행 파일을 테스트하기 전에 어느 단계에서 변경이 발생했는지 파악하는 데 도움이 됩니다.

## 회귀 체크는 성공적인 프로그램과 의도적인 거부를 모두 포괄합니다

[테스트 가이드](https://github.com/EMI-Group/genesis-demo-jcc/blob/a8c116ec7ed3d59479ad3be8fed3e63384f50a87/docs/testing.md)는 종료 상태와 출력을 확인하는 컴파일 후 실행(compile-and-run) 케이스와 함께, 진단 심각도, 메시지 및 소스 범위를 확인하는 컴파일 실패(compile-fail) 케이스를 설명합니다. 최적화 패스 또한 표현 검증 체크를 거칩니다.

따라서 후속 모델은 하나 이상의 수락 조건을 가집니다. 실행 파일을 생성하더라도 출력이 변경되면 불충분하며, 언어 정책상 거부해야 하는 프로그램을 수용하는 것 또한 불충분합니다. 진단 테스트는 성공 여부만 따지는 벤치마크가 놓칠 수 있는 동작을 보존합니다.

[버전 관리되는 README](https://github.com/EMI-Group/genesis-demo-jcc/blob/a8c116ec7ed3d59479ad3be8fed3e63384f50a87/README.md#feature-status)에는 부분적인 `long double` 산술 연산 및 보류된 타겟과 같은 구체적인 제한 사항이 나열되어 있습니다. 이러한 제한 사항은 유용한 상속 정보입니다. 문서화된 거부 대상을 변경하는 것은 기능적 결정이지, 자동으로 회귀 수정이 되는 것은 아닙니다.

## LLVM 하네스가 실제로 비교하는 것

공개된 [LLVM-suite 러너](https://github.com/EMI-Group/genesis-demo-jcc/blob/a8c116ec7ed3d59479ad3be8fed3e63384f50a87/tools/llvm-suite/run.py)는 테스트 대상 컴파일러로 스위트를 구성하고, 실행 파일을 빌드하며, 그 출력을 참조 파일과 비교합니다. 직접적인 비교는 공백 토큰을 기준으로 합니다. 비수치 토큰은 정확히 일치해야 하며, 수치 토큰은 기본값 1e-4의 설정 가능한 부동 소수점 허용 오차를 사용합니다. 최종 종료 코드는 정확히 일치해야 합니다.

이는 테스트 카운트에 매니페스트와 비교 정책이 필요한 이유를 보여줍니다. 러너에 문서화된 36개 케이스의 Regression/C 서브셋은 연속성 기록의 1,820개 유지 케이스와는 다른 평가 범위입니다. 더 작은 스냅샷을 사용하여 핸드오프의 시작 통과율을 추론할 수 없으며, 두 합계를 빼는 것으로 진행 상황을 측정할 수도 없습니다.

## 보고된 핸드오프 결과를 해당 범위에 귀속시키십시오

| 항목 | 연속성 기록 보고 내용 |

| 모델 전환 | GLM 5.2 → DeepSeek V4 Flash |
| 전달된 대화 컨텍스트 | 0 |
| 보존된 프로젝트 상태 | 승인된 컴파일러 계보 |
| 작업 재귀 깊이 | 4 → 8 |
| 최종 평가 | 1,820/1,820 유지된 LLVM SingleSource 케이스 |

출처: [GW-000002](https://genesis.evox.group/evidence/compiler-continuation/). 이는 단일 핸드오프에서 프로젝트가 보고한 결과입니다. 재귀 깊이는 작업 분해를 설명하며, 테스트 결과는 동작에 대한 증거를 제공합니다.

초기 컴파일러 기록과 연속성 기록은 동일한 리포지토리를 링크합니다. 이를 두 개의 독립적인 컴파일러 프로젝트로 계산해서는 안 되며, 서로 다른 범위의 테스트 합계는 분리되어 유지되어야 합니다.

## 핸드오프를 조사 가능하게 만들기

이 접근 방식을 적용하는 개발자에게 유용한 핸드오프 패키지는 승인된 리비전, 빌드 명령, 인터페이스 규약, 정확한 회귀 매니페스트 및 알려진 제외 사항으로 구성됩니다. 이는 실험을 위해 이러한 형태의 완전한 패키지가 아카이브되었다는 주장이 아니라, 공개된 아키텍처와 하네스에서 도출된 실질적인 권장 사항입니다.

작은 변경부터 시작하여 중간 결과물, 진단 메시지 및 실행 파일 동작을 해당 리비전과 비교하십시오. [Genesis 개발 이력 뷰](/news/genesis-development-history)는 작업을 수행한 에이전트가 종료된 후의 기여 사항을 추적할 수 있는 관련 컨텍스트를 제공합니다.
