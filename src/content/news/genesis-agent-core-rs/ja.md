openJiuwen Agent Core は、モデル呼び出し、ツール、ワークフロー、セッション状態をつなぐ Agent アプリケーション向け Python SDK です。EvoX Genesis が [2026 年 11 月 20 日に公開した Evidence][evidence] は、Python SDK v0.1.20 を読み取り専用の参照として Rust 実装 **agent-core-rs** に変換した過程を記録しています。

成果物は **30 の Rust crate と 26 の実行可能なサンプル**を持つワークスペースです。最初の変換に続き、保持したコードを別のタスクで継続開発しました。技術的な焦点は、言語を変えてもどの動作が維持されるかです。保存済みセッションの復元、承認を待つツール、意図した分岐を通るワークフローが求められます。

![Python コードを Rust に変換し、対応するワークフロー分岐を保つ概念図](./contract-migration-v2.webp)

## 実装を変えて契約を維持する

ワークスペースは共有型、モデルとツールへのアクセス、セッション状態、オーケストレーション、アプリケーション入口に分かれます。実行可能な成果物にはワークフロー、DeepAgent、チーム協調、CLI が含まれます。30 crate という数は、Agent アプリケーションの複数の構成要素に変換が及ぶことを表しており、各連携の対応範囲は[対応表][parity]で確認できます。

[リビジョン 242b5b5 のソース][repo] は、Card JSON のフィールド、モデル通信形式、永続化セッション、ワークフロー参照、CLI の動作を互換性の対象とします。Rust の型と trait、Tokio による非同期実行、Serde のシリアライズが Python の実装機構を置き換えます。共有型は利用側より下層に配置し、umbrella crate は API を再エクスポートして動作の重複を避けます。

互換性は実装済みの部分集合に限られます。[対応表][parity] は、対応済み、部分実装、未対応の領域を区別しています。分散実行、GPU/ML、ベンダーや外部サービスとの一部連携は保留中です。型付きの Unsupported 経路がある場合は明示的なエラーを返し、それ以外には実装自体がない箇所もあります。移行するアプリケーションの選定には、この違いが関わります。

## セッションを復元し、ツールを待機させる

[セッションのサンプル][session] は、一時ストレージにチェックポイントを保存し、同じ識別子と保存先で新しいセッションを作って状態を復元します。これはストレージ境界を越える検証です。元のオブジェクトをメモリに残すだけでは、同じ性質を確認できません。

承認のシナリオでは、模擬ツールの呼び出し前にゲートを設け、承認待ちの間に実行カウンターが増えないことを確認します。対応する承認データを付けて再呼び出しすると、実行が進みます。スクリプト化したモデルと計測用ツールにより、プロバイダーの認証情報なしで順序を確認できます。

[ワークフローのサンプル][workflow] は別の統合課題を扱います。同じコンパイル済みトポロジーで、二つの入力が短い分岐と長い分岐を通り、ノードのフィールド参照で値を渡します。相互排他的な先行ノードを単純に一つのノードへ接続すると、両方を待つ論理積になります。転送コンポーネントと明示的なルート有効化により、どちらの分岐も共通の終点へ到達させます。フィールド名の維持だけでは、このスケジューリング問題を見逃します。

## 2 件のタスクと費用の範囲

[タスク履歴の付録][history] によると、最初の変換は 11 月 11～16 日 UTC に実行され、出力を残して手動停止されました。その後、11 月 19 日 UTC の進化タスクが完了しました。DeepSeek V4 Flash に帰属する 2 件のモデル呼び出し費用は合計 **150.024283 米ドル**です。 2 件目のタスクは最初の結果リビジョンから再開しており、タスクの境界を越えて既存の実装を保持し、その上で開発を進める流れを示しています。

待機とキューを含むタスクの経過時間は合計 **113 時間 42 分**ですが、最初の開始から最終完了までの暦上の期間は 8 日を超えます。3,570 の Agent 登録は累積数であり、最大同時実行数ではありません。インフラ、人手、後の文書作業は費用に含まれません。途中で失敗したタスクは使用量が不明なため除外されています。

付録は、製品コード、テスト、サンプルに含まれるコメントと空行を合わせて、Rust の物理行数を 1,434,767 としています。これは成果物の規模であり、保持された動作は別途検証で判断します。

## 検証記録が示すこと

[検証記録][parity] は、整形、Clippy、オフラインのワークスペーステスト、Rustdoc、7 組の feature 検証、サンプルビルドの成功を報告しています。**24,293 はソース内のテスト関数数**であり、実行時の合格件数ではありません。無視された 5 項目は補助処理または環境依存のプローブです。後続の文書タスクで再実行したのは一部の検証のみです。

スクリプト化モデル、ローカル模擬サーバー、一時ストレージ、ループバックソケットでプロトコルと実行動作を検証します。実際の認証情報なしで再現性を確保できますが、実モデルによるタスク成功率は別の評価です。結果はプロジェクトによる報告であり、私たちは Rust テストを独立に再実行していません。

## 高速化は測定した負荷の範囲で読む

[ベンチマーク][bench] は、8 論理 CPU の Linux ホスト 1 台で、ウォームページキャッシュ下の Rust release ビルドと CPython 3.11.15 を比較しています。プロンプト描画は **0.356 µs 対 16.37 µs**で約 **46 倍**、I/O のない 2 ノードグラフは **7.23 µs 対 112.3 µs**で約 **15 倍**です。

繰り返しバッチを操作当たりに換算し、Rust のバッチは 10 倍の大きさです。グラフの論理構造は同じですが、内部エンジンは異なります。比率はローカルなフレームワーク負荷を表し、モデル・ネットワーク遅延、コールドキャッシュ起動、並行スケーリングを含みません。Python の初回グラフと Rust のスクリプト化 Agent は異なる負荷であり、対応した起動時間・メモリ比率は算出できません。

## 保持したい動作から始める

移行評価では、チェックポイント、承認、条件分岐を受け入れ基準にできます。[対応表][parity] で必要な連携を確認し、ビルド環境を整えて文書の `make verify` を実行してください。`cargo test --workspace --offline --no-fail-fast` は、単なる `cargo test` では省略される開発用 crate も含みます。

ワークスペースはソースで提供され、crate は `publish = false` です。[Evidence 全文][evidence] と[固定リビジョンの実装][repo] を参照できます。以前の [MESA 再開発](/ja/news/genesis-mesa) と合わせ、実装の生成に加えて保持された動作から Genesis を評価する道筋を示しています。
