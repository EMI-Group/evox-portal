构建张量图编译器意味着要保持同一计算的多种实现之间的一致性。图转换可能会改变张量布局；适配器可能会拒绝某项操作；设备调用可能会在计算完成前返回。EvoX Compiler 的公开源码把这些问题拆成了可检查的接口与测试，也让 Genesis 的开发成果有了更具体的观察入口。

![用回归测试核对编译器计算图](./compiler-contract-layers.webp)

[10 月 28 日的 Evidence 快照](https://genesis.evox.group/evidence/evoxc/)记录了 6,789 项测试通过，以及约 50 美元的模型 token 费用。为了分析这些数字背后的工程设计，本文还参考了公开可用的 v0.1.0 源码。快照和发布版本的测试总数有所不同；下文中的实现示例均按其版本进行了标识。

## 将目标转化为可测试的接口

EvoX Compiler 负责张量语言、EvoXIR 图以及分阶段执行接口。外部编译器接收其导出的表示，并处理优化、调度和代码生成。其[包契约](https://github.com/EMI-Group/evoxc/blob/v0.1.0/CONTEXT.md)记录了依赖方向：值类型和 IR 支撑追踪与算子实现，图变换和后端适配器再建立在这些基础之上。独立的 `evoxc_hf` 包调用公开的编译器 API；编译器本身不导入模型集成部分。

这种划分给每项局部开发任务设定了具体边界。例如，转换操作会生成另一个普通图，而不是要求每个后端都理解 Python 的 `vmap`。后端尚不支持的情况必须通过明确的错误报告，而不是静默地改变执行路径。包级上下文文档记录了另一个开发任务必须遵守的 API 和约束。

公开的流水线为 `trace → lower → compile → load → run`。每个阶段都会返回一个独立的对象。[规范测试](https://github.com/EMI-Group/evoxc/blob/v0.1.0/tests/test_spec_compliance.py)会检查传给错误阶段的输入，并拒绝把图定义当作即时执行函数直接调用，并验证便捷函数是否展开为文档记录的流水线。测试还会拒绝从闭包中捕获具体张量，除非作者显式地嵌入它。这样做在实践中的好处是，看似方便的快捷方式不会悄悄引入第二套语义。

根据 Evidence 记录，开发工作是逐层推进的，在继续下一层之前必须通过 pytest 检查。该仓库为这种方法提供了可检查的契约和测试；它不提供完整的智能体决策存档序列。

## 针对两个参考标准检查种群转换

一个要求很高的特性是 `batch_functions`：将具有匹配输入/输出签名的多个程序合并为一个图。它的契约比“合并后的图能运行”更强：输出的第 i 行必须仍然等于程序 i 的结果。

[v0.1.0 集成测试](https://github.com/EMI-Group/evoxc/blob/v0.1.0/tests/transforms/test_batch_functions_integration.py)采用了一个简短、易读的示例。在相同的图位置，三个程序分别执行 `x + 1`、`x * 2` 和 `x - 3`。当 `switch_ops=True` 时，合并后的图通过逐行选择来表示不同的操作。测试通过 IREE 的 CPU 路径编译该图，并将其输出与合并图的 NumPy 执行结果以及原始函数的堆叠 NumPy 结果进行对比，误差容限设为 `rtol=atol=1e-5`。

不依赖外部编译器的检查会确认 StableHLO 输出中是否存在预期的选择操作。另一个检查则合并相同的程序并将其结果与 `vmap` 进行对比，在这种情况下不应需要选择操作。这些测试共同检查计算语义是否保持、导出是否正确、后端是否能够集成，而不是仅将成功编译作为唯一的验收条件。

## 设备放置是正确性的一部分

GPU 可执行对象接收的数据，必须真实位于相应设备上；给主机数据换一个设备标签不能替代传输。[张量与放置规范测试](https://github.com/EMI-Group/evoxc/blob/v0.1.0/tests/test_spec_compliance.py)会检查数据的真实存放位置，传输是否通过 `Tensor.to(device)` 显式进行，以及无效的放置是否会触发 `DeviceError`。

这对性能测量也至关重要。如果每次调用都重新传输模型权重，那么延迟数据测量的任务负载就与保持权重驻留的任务负载完全不同。[v0.1.0 模型集成文档](https://github.com/EMI-Group/evoxc/blob/v0.1.0/evoxc_hf/CONTEXT.md)将模型检查点加载、前向计算和可执行对象的分阶段构建分开。参数保持为显式的图输入，使其放置位置清晰可见。

## 返回的调用并不一定意味着工作已完成

XLA 的设备常驻执行路径可以先提交任务，再在计算完成前返回。因此，如果仅对 `run` 计时，会低估执行时间。[同步测试](https://github.com/EMI-Group/evoxc/blob/v0.1.0/tests/backends/test_xla_synchronize.py)检查事件生命周期：运行会累积完成句柄；`synchronize()` 等待并销毁它们；再次同步时不会重复调用插件处理已完成的事件。

错误情况也同样具体。如果等待失败，剩余的句柄仍必须被处理，并抛出第一个错误。不提供完成事件的插件必须触发显式错误，而不是虚假的完成声明。

这些测试使用了一个不进行数值计算的小型伪 PJRT 插件。它们验证的是同步语义和清理工作，而不是 GPU 吞吐量或数值精度。这种区分使测试的证据与声明相匹配。
