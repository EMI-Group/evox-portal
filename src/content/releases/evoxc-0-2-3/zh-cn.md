EvoX Compiler v0.2.3 于 2026 年 11 月 25 日（UTC）发布，提供 Python wheel 和源码归档。简短的 GitHub 说明链接到 v0.2.2 至 v0.2.3 的差异；版本化变更日志则记录了通向本次分发的 0.2 系列主要变化与打包修复。对于从 0.1 升级的用户，重点是安装哪一对编译器和运行时、如何选择物理设备，以及需要重新检查哪些数值行为。[版本发布][release] · [变更日志][changes]

## 让编译器与运行时保持配套

IREE 可选依赖现在要求编译器和运行时均为 3.13.0 至低于 3.14 的版本。编译产物具有版本依赖性，不能假定另一组编译器和运行时生成的文件可以原样加载。上游记录重新验证了 llvm-cpu，以及 AMD Instinct MI300X、ROCm 7.1 环境中的 ROCm/HIP，包括此前 IREE 版本失败的循环和扫描。这些检查并不自动涵盖 CUDA、多 rank 执行或所有模型基准。[版本化依赖要求][requirements] · [变更日志][changes]

适配器也明确控制设备到主机的结果回读，不再直接依赖运行时的快捷路径。这关系到程序计算正常、却在取回结果时失败的情况。主机内存可以保留映射路径；设备缓冲区需要显式传输。评估应用工作负载时，应计入传输时间，并将其与内核执行时间分开。

## 先发现 XLA 插件，再选对设备

XLA 注册不再在调用方提供路径之前执行不带选项的插件探测。发现过程依次考虑显式插件选项、对应环境变量、已知位置及已安装的 JAX 插件包，而不导入 JAX 本身。可用性检查移至选项已经齐备的编译和加载阶段。构建辅助函数也会把解析后的选项传给加载过程，修复编译时找到插件、加载时却丢失配置的问题。[后端指南][guide]

ROCm 插件必须服务于 ROCm 设备，CUDA 插件必须服务于 CUDA 设备。提供 GPU 插件却保留默认 CPU 选择会被拒绝。进行 GPU 实验时，应选择对应设备，并显式把张量移过去。把结果复制回主机之前，先检查输出所在设备。XLA 执行失败时也会清空缓存的输出指针槽，避免后续调用复用失效缓冲区指针。

## 比较速度之前，先复核语义

NumPy 参考解释器使用缓存的分派计划，在最后一次使用后释放不再需要的中间值，并共享不可变的主机设备实例。这些变化减少准备和分配开销，无需改变公开调用方式。变更日志中的 TensorNEAT 测量针对特定工作负载，不能当作通用加速倍数。

编译后的余数运算现在遵循 NumPy floormod：结果符号与除数一致。因此，负数输入适合作为升级检查。保留固定输入和参考输出，再用适合数据类型的容差比较解释器与编译器结果。打包修复接受 maturin 附带的共享库目录，并将经过测试的分发文件平铺到暂存目录，解决阻止产物发布的问题。[修复记录][changes]

## 在干净环境中升级

需要 Python 3.11 或更新版本。使用 pip 安装 release 资源中选定的 0.2.3 wheel；该版本提供 Linux、macOS 和 Windows wheel 和源码归档。IREE 可选依赖可用 `pip install "evoxc[iree]==0.2.3"` 安装，并确认 IREE 依赖成对匹配。独立的 evoxc-hf 分发包使用自己的版本号。运行 `pip check`，查看已安装版本，再复核一个代表性计算图、一个负数余数案例和一次设备往返传输，然后迁移更大的工作负载。[安装指南][guide]

有关这些后端周围的计算图变换、自定义算子和显式编译阶段，可结合本版本文档阅读[自定义编译专题][related]。
