会話、開発タスク、Git の変更を行き来するたびに、プロジェクトの文脈を作り直す必要はないはずです。2026 年 11 月 20 日に `main` へマージされた Genesis PR #175 は、プロジェクトナビゲーション、タブ、タスクと会話の履歴、Git ペイン、その場で開ける設定を備えた LiveView ワークベンチを導入しました。関連するワークスペースと下書きスコープの変更により、プロジェクトの識別情報を各画面で引き継げます。[マージ済みの変更][pr]

*概念図：各プロジェクトが固有の作業文脈を保持します。*

## 一つの場所でプロジェクトを確認する

ワークベンチはナビゲーションと作業画面をつなぎます。プロジェクトへ戻り、タスクや会話の履歴を確認して Git の変更を見る際、各画面を別々の出発点として扱う必要が減ります。既存のワークスペース選択、アカウント設定、タスクの一時停止・再開は維持され、再接続後には承認の文脈も復元されます。[従来の Assistant タスクフロー][previous]を継ぐ連続性の改善であり、どの操作を許可するかは引き続き構造化された承認が決定します。[統合内容][pr]

たとえば、ライブラリとそれを使うアプリケーションを交互に開発する場合です。アプリのタブを開いても、ライブラリ向けの要求の下書きはライブラリに残るべきです。Git 操作も、選択したプロジェクトのサーバーとリポジトリを対象にする必要があります。マージ済みの変更は Git 操作前にプロジェクトの所属を確認し、接続できない場合も選択したノードを保持します。操作先をダッシュボードのホストへ差し替えません。

## 下書きの識別情報はパスだけではない

共通の `DraftScope` はブラウザーの下書きを `{node, token}` で定義します。Virtual Context Tree にマウント済みのプロジェクトは `vct:///projects/<name>` を使い、未登録なら OS の絶対パスを使います。両方がある場合は VCT ポイントが優先されます。同じマウント済みプロジェクトを異なるパス表記で選んでも同じ下書きに到達し、同一パス上の異なる VCT ポイントは別々に扱われます。[実装][scope]

ブラウザーの保存キーはノードとトークンの組み合わせです。後続の修正では VCT ポイントが利用可能になった時点でパス単位の下書きを引き継ぎ、ディレクトリ選択からプロジェクト登録への移行に対応します。これはブラウザー内の下書きの連続性であり、タスクの永続化やサーバー再起動後の会話の永続的な復元を保証するものとは別です。[下書きの引き継ぎ][adopt]

リモートプロジェクトでは、パスをそのまま保持することも重要です。ブラウザー側ホストのファイルシステム規則で正規化してはいけません。復元した下書きを送る前に、特にローカルとリモートを切り替えた後は、ノード、リポジトリ、モデルを確認してください。

## ワークスペースはグループ、タスクには実ディレクトリが必要

VCT に `vct:///workspaces/<name>` というグループ層が加わりました。ワークスペースは順序付きメンバー一覧と任意の説明を持ちます。メンバーはプロジェクトのマウントポイントまたは OS パスを参照し、ワークスペースの入れ子はできません。Projects パレットと Assistant の選択画面にグループを表示でき、読み取り専用 API でメンバーを確認できます。[操作インターフェース][workspace]

グループ自体には実行ディレクトリがありません。そのためワークスペースだけを選択した場合、`DraftScope.path/1` はパスを返さず、タスクの受付も VCT ポイントをタスクパスとして拒否します。ライブラリとアプリの例では、両方をまとめて閲覧できるようにグループ化し、開発タスクを開始するときは具体的なメンバープロジェクトを選びます。グループ化によって全メンバーが暗黙の書き込み先になるわけではありません。

ソースチェックアウトでは `mix vct.workspace list` と `mix vct.workspace show <name>` でグループを調べられます。文書化された `create` は複数の `--member` と任意の `--data-dir` を受け付けます。対象 Genesis インスタンスのデータディレクトリを指定してください。見つからないメンバーも黙って省略せず報告します。グループ変更前にリンク先のコマンド仕様を確認してください。

## 画面間の引き継ぎを確認する

PR には、タスク作成と完了、Assistant のキーボード送信とストリーミング、アカウント設定画面のブラウザー確認が記録されています。一方、プロジェクトに限定した Assistant のタスク照会でタイムアウトした記録もあります。長い処理では、要求が受理されたことと結果を観測できたことは別の出来事です。[検証記録][pr]

変更を含むビルドで、二つのプロジェクトに異なる下書きを残し、選択したノードへ再接続して、対象の Git ペインを開いてみてください。下書きが正しいプロジェクトへ戻り、承認が実際の実行先を示しているか確認します。その後はタスクの記録された状態を追い、タブの復元だけでバックグラウンド作業の完了を判断しないようにします。
