高速な遺伝的プログラミングのカーネルだけでは、使える探索システムにはなりません。手元の GPU が対応し、進捗表示が各世代の時間を占めないことも必要です。EvoGP の [2026 年 10 月 16 日のマージ][s1] は標準パイプラインの Python レベルの適応度縮約を置き換えます。先行する [6 月 17 日の AMD ROCm 対応][s2] と合わせ、同じ木構造探索の利用範囲を広げます。

![異なる二つのアクセラレーターボード上に同じプログラム木](./cover.webp)

*概念図：同じプログラム表現が GPU バックエンドをまたぎます。*

## 集団統計をテンソル演算に保つ

適応度テンソルに対する Python 組込みの最大・最小計算を `torch.max` と `torch.min` に変更します。大きなデバイステンソルを Python で走査する処理は言語境界の負担を生みますが、テンソル縮約なら数値フレームワーク内で処理できます。適応度関数が軽い場合に特に重要です。

大集団の記号回帰では式の評価が並列でも、各世代の極値表示が意外に高価になり得ます。修正は統計の意味を保ちながらこの不均衡を解消します。PR は百万個体の例で大幅改善を報告していますが、完全な測定手順はありません。実用上は表示も含む世代全体を計測することが重要です。

## CUDA と ROCm で同じソースを使う

6 月の統合は PyTorch のビルド時 HIP 変換を使い、CUDA 拡張ソースを AMD GPU 向けにコンパイルします。バックエンド別のコンパイル設定と CUDA 専用ヘッダーの保護により、HIP ビルドを可能にします。ROCm 版 PyTorch があれば別のアルゴリズム実装を維持する必要がありません。

木インタープリターの動的デバイススタック割当ても固定長のローカル配列に変更しました。貢献者は AMD の誤動作を、同時常駐する wavefront 間の割当ての別名化に追跡しました。他スレッドの一時状態を使えば適応度が誤り、選択も損なわれるため、スレッドごとの分離が重要です。

## バックエンドに合わせてビルドする

[ソース導入説明][s3] は GPU ツールチェーン、C++ コンパイラー、対応する PyTorch を要求します。AMD では `hipcc` を含む ROCm と ROCm PyTorch を使います。`--no-build-isolation` でソースから構築すると、導入済み PyTorch 環境で拡張をビルドできます。

ROCm でも例のデバイス文字列は `cuda` のままです。これは PyTorch のインターフェースです。特定の AMD アーキテクチャーは `PYTORCH_ROCM_ARCH` で指定します。これはビルド設定であり、木表現や進化演算子を書き換える要求ではありません。

## 小さい探索を確認してから拡大する

PR は AMD MI250X、W7800、RX 9070 XT、PRO V710 での記号回帰検証を報告し、OS と ROCm 版を記載しています。1,000 個体、100 世代、固定シードの実行であり、その構成についてのプロジェクト報告です。全ハードウェアでの性能保証ではありません。

構築後は `python -m evogp.sr_test` を実行し、有限の適応度と正常終了を確認します。次に入力、シード、個体数を固定し、表示の有無を比較して評価器と管理処理の費用を分けます。[EvoGP 研究概要][related] がテンソル化された木を説明し、二つの改良がその表現から利用可能なハードウェア上の探索までをつなぎます。
