openJiuwen Agent Core는 모델 호출, 도구, 워크플로, 세션 상태를 연결해 Agent 애플리케이션을 만드는 Python SDK입니다. EvoX Genesis는 [2026년 11월 20일 공개한 Evidence][evidence]에서 Python SDK v0.1.20을 읽기 전용 참조로 사용해 Rust 구현 **agent-core-rs**로 변환한 과정을 기록했습니다.

결과는 **Rust crate 30개와 실행 가능한 예제 26개**로 구성된 워크스페이스입니다. 초기 변환 이후 보존된 코드를 바탕으로 후속 작업을 진행했습니다. 핵심 기술적 질문은 언어가 바뀌어도 어떤 동작이 유지되는가입니다. 저장한 세션이 정확히 복원되고, 도구가 승인을 기다리며, 워크플로가 의도한 분기를 따라야 합니다.

![Python 코드를 Rust로 변환하며 대응하는 워크플로 분기를 유지하는 개념 그림](./contract-migration-v2.webp)

## 구현을 바꾸면서 계약을 유지하기

워크스페이스는 공유 타입, 모델과 도구 접근, 세션 상태, 오케스트레이션, 애플리케이션 진입점으로 나뉩니다. 실행 가능한 산출물은 워크플로, DeepAgent, 팀 협업, CLI를 포함합니다. crate 30개라는 수치는 변환이 Agent 애플리케이션의 여러 구성 요소에 걸쳐 있음을 보여 주며, 각 통합의 지원 범위는 [호환성 표][parity]에 명시돼 있습니다.

[리비전 242b5b5의 소스][repo]는 Card JSON 필드, 모델 통신 형식, 영속 세션 데이터, 워크플로 참조, CLI 동작을 호환성 목표로 삼습니다. Rust 타입과 trait, Tokio 기반 비동기 실행, Serde 직렬화가 Python의 구현 방식을 대체합니다. 공유 타입은 사용하는 계층보다 아래에 두고, umbrella crate는 API만 다시 내보내 동작을 중복 구현하지 않습니다.

호환성은 구현된 부분집합에 한정됩니다.[호환성 표][parity]는 지원 인터페이스, 부분 구현, 보류 영역을 구분합니다. 분산 실행, GPU/ML 경로, 일부 공급업체 및 외부 서비스 통합은 보류 상태입니다. 타입으로 정의된 Unsupported 경로가 있으면 명시적 오류를 반환하며, 다른 공백에는 구현 자체가 없습니다. 이 차이는 이식할 애플리케이션을 선택할 때 중요합니다.

## 복원되는 세션과 기다리는 도구

[세션 예제][session]는 체크포인트를 임시 저장소에 저장한 뒤 같은 식별자와 저장 루트로 새 세션을 만들어 상태를 복원합니다. 저장소 경계를 넘는 검사입니다. 기존 세션 객체를 메모리에 유지하는 것만으로는 같은 속성을 입증할 수 없습니다.

승인 시나리오는 모의 도구 호출 앞에 관문을 두고 실행 카운터로 승인 대기 중 도구가 실행되지 않았는지 확인합니다. 해당 승인 데이터를 넣어 다시 호출하면 실행이 진행됩니다. 스크립트 모델과 계측 도구 덕분에 공급업체 인증 정보 없이도 순서를 확인할 수 있습니다.

[워크플로 예제][workflow]는 다른 통합 문제를 검사합니다. 두 입력이 같은 컴파일된 토폴로지의 짧은 분기와 긴 분기를 거치고 노드 필드 참조로 값을 전달합니다. 상호 배타적인 두 선행 노드를 하나의 노드에 단순히 연결하면 양쪽을 모두 기다리는 AND 조건이 됩니다. 전달 컴포넌트와 명시적 경로 활성화를 사용해 어느 분기에서든 공통 종점에 도달합니다. 필드 이름만 보존하면 이런 스케줄링 문제를 놓칠 수 있습니다.

## 두 작업과 명확한 비용 범위

[작업 이력 부록][history]에 따르면 초기 변환은 UTC 11월 11~16일 진행됐고, 결과를 보존한 채 수동 중단됐습니다. 이어 UTC 11월 19일 진화 작업이 완료됐습니다. 두 작업에서 DeepSeek V4 Flash에 귀속된 모델 호출 비용은 총 **150.024283달러**입니다. 두 번째 작업은 첫 작업의 결과 리비전에서 재개됐으며, 작업 경계를 넘어 기존 구현을 보존하고 그 위에서 개발을 이어 가는 방식을 보여 줍니다.

대기와 큐를 포함한 작업 경과 시간은 합계 **113시간 42분**이지만, 첫 시작부터 최종 완료까지 달력상 기간은 8일을 넘습니다. Agent 등록 3,570개는 누적 수로 최대 동시 실행 수가 아닙니다. 인프라, 사람의 작업, 후속 문서 작업은 비용에서 제외됩니다. 중간에 실패한 작업도 사용량이 알려지지 않아 제외됐습니다.

부록은 제품 코드, 테스트, 예제를 합친 Rust 물리적 행 수를 1,434,767로 집계하며 주석과 빈 줄도 포함합니다. 이는 산출물 규모를 설명하며, 재개발이 어떤 동작을 보존했는지는 동작 검증으로 판단합니다.

## 검증 기록이 보여 주는 범위

[검증 기록][parity]은 포맷, Clippy, 오프라인 워크스페이스 테스트, Rustdoc, feature 그룹 7개, 예제 빌드가 통과했다고 보고합니다. **24,293은 소스의 테스트 함수 수**이며, 실행에서 수집한 통과 건수가 아닙니다. 무시된 항목 5개는 보조 프로그램이나 환경 의존 탐침입니다. 후속 문서 작업에서는 일부 검사만 다시 실행했습니다.

스크립트 모델, 로컬 모의 서버, 임시 저장소, 루프백 소켓으로 프로토콜과 런타임 동작을 검사합니다. 실제 인증 정보 없이 반복할 수 있지만 실제 모델의 작업 성공률은 별도 평가 대상입니다. 이는 프로젝트가 보고한 결과이며, 저희가 Rust 테스트를 독립적으로 다시 실행한 것은 아닙니다.

## 속도 향상은 측정한 작업 안에서 해석하기

[벤치마크 보고서][bench]는 논리 CPU 8개인 Linux 호스트 한 대에서 따뜻한 페이지 캐시 조건으로 Rust release 빌드와 CPython 3.11.15를 비교합니다. 프롬프트 렌더링은 **0.356 µs 대 16.37 µs**로 약 **46배**, I/O 없는 2노드 그래프는 **7.23 µs 대 112.3 µs**로 약 **15배** 빠릅니다.

반복 배치의 시간을 연산당 값으로 환산하며 Rust 배치 크기는 10배입니다. 그래프의 논리 구조는 같지만 내부 엔진은 다릅니다. 이 비율은 로컬 프레임워크 오버헤드이며 모델·네트워크 지연, 콜드 캐시 시작, 동시성 확장을 포함하지 않습니다. 별도의 Python 첫 그래프 실행과 Rust 스크립트 Agent 프로세스 측정은 서로 다른 작업이므로 동등한 시작 시간이나 메모리 개선 비율을 산출할 수 없습니다.

## 보존해야 할 동작에서 시작하기

이식 평가에는 체크포인트, 승인, 조건부 라우팅 예제를 구체적인 인수 기준으로 활용할 수 있습니다. [호환성 표][parity]에서 필요한 통합을 확인하고 빌드 환경을 준비한 뒤 문서의 `make verify`를 실행하십시오. `cargo test --workspace --offline --no-fail-fast`는 일반 `cargo test`에서 빠지는 개발 crate도 포함합니다.

워크스페이스는 소스로 배포되며 crate에 `publish = false`가 설정돼 있습니다. [전체 Evidence][evidence]와[고정 리비전 구현][repo]에서 산출물을 살펴볼 수 있습니다. 앞선 [MESA 재개발](/ko/news/genesis-mesa)과 함께, 새로운 구현뿐 아니라 보존한 동작으로 Genesis의 재개발을 평가하는 방법을 보여 줍니다.
