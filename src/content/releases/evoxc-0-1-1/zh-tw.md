搜尋程式時，編譯本身就是實驗預算的一部分。如果每一代都花很久準備計算圖，僅加快裝置執行只能解決部分問題。2026 年 10 月 30 日釋出的 [EvoX Compiler v0.1.1][s1] 改進了準備路徑，並修復後端故障場景。[包含 45 次提交的變更集][s2] 延續了 v0.1.0 的顯式計算圖流水線。

![不同程式結構被整理成緊湊的並行分組](./cover.webp)

*概念插畫：在編譯前組織一個程式種群。*

## 程式分組需要成本模型

種群變換 `batch_functions` 將相容的候選程式組合為一張圖。v0.1.1 在內部類別圖中傳播行依賴，並擴充套件 `bands="auto"` 使用的幾何分組搜尋。這有助於變換判斷哪些計算依賴具體種群成員，以及應如何組織候選程式。

在遺傳程式設計實驗中，候選程式可能具有相同輸入規格，卻包含不同運算。單一扁平分組不一定最省計算。分組提供另一種組織方式，自動策略透過成本模型比較方案。關鍵仍是語義檢查：合併結果第 i 行應與單獨執行候選程式 i 一致。此次釋出同步更新了相關回歸測試。

## 消除計算圖準備中的重複工作

多項改進針對裝置執行前的 CPU 工作：透過直接遍歷棧幀捕獲原始碼位置，移除降級階段重複的驗證，並在 IR 驗證中使用線性使用關係追蹤及結果型別推斷快取。StableHLO 匯出還增加了常量文字批次輸出、型別文字快取和表驅動運算分派。

這些改進位於不同階段。匯出加快不等於 GPU 核心本身更快。比較版本時，應分別測量追蹤、變換、降級、編譯和穩態執行。包含大量常量的大種群，與數值核心昂貴的小圖，可能受不同成本主導。

## 後端故障更容易定位

IREE 介面卡現在把單次分派的 HAL 繫結數量限制報告為可採取行動的 `BackendError`，幫助區分後端資源限制和數值程式錯誤。XLA 介面卡則不再跨越 `PJRT_Client_Create` 持有共享客戶端鎖，修復同執行緒終結器導致的死鎖，並增加回歸測試。

後端支援仍以版本化支援矩陣為準。NumPy 提供 CPU 直譯器；IREE、XLA 和 TVM 的依賴與裝置要求不同，因此可以先用直譯器結果建立參考，再檢查編譯路徑。[版本 README][s3] 說明了這些邊界及顯式裝置傳輸模型。

## 圍繞一個代表性種群升級

基礎包可使用 `pip install evoxc==0.1.1`；IREE 環境可使用 `pip install "evoxc[iree]==0.1.1"`。需要 Python 3.11 或更新版本。獨立發行包 `evoxc-hf` 有自己的版本和升級週期；應保留原實驗所用的後端外掛配置。

從儲存的種群和固定輸入開始，將合併輸出與逐個程式的參考執行比較，再分別測量準備和執行時間。若加速器報告繫結錯誤，保留計算圖及後端資訊用於診斷，不要悄悄改變實驗。[v0.1.0 介紹][related] 解釋整體流水線；v0.1.1 則讓準備階段和後端邊界更便於實際使用。
