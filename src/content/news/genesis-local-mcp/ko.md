코딩 에이전트가 이미 목표와 프로젝트 경로를 알고 있을 수 있습니다. 다른 엔진에 실행을 맡기려면 같은 대화에서 작업을 시작하고 진행 상황을 확인하고 결과를 가져올 수 있어야 합니다. 2026년 11월 11일, Genesis는 로컬 모델 컨텍스트 프로토콜(MCP) 엔드포인트를 `main`에 병합했습니다. 호환되는 코딩 에이전트는 한 연결로 기존 Genesis 작업 API에 접근할 수 있습니다. [병합된 변경 사항][pr]

![같은 작업대 위의 두 단말이 작업 표와 그에 대응하는 결과를 주고받는 모습](./genesis-local-mcp.webp)

*코딩 에이전트와 Genesis가 같은 컴퓨터에서 작업을 인계하는 장면을 그린 편집 삽화입니다.*

## 작업을 실행하는 Genesis 프로세스에 연결하기

Streamable HTTP 엔드포인트 `/mcp`는 실행 중인 Genesis 서버에 탑재됩니다. 서버는 클라이언트의 요청을 인증하고 인자를 검증한 다음 기존 작업 또는 스케줄러 API를 호출합니다. HTTP 요청이 끝난 뒤에도 서버에서 작업은 계속됩니다. 연결은 무상태이므로 나중에 다시 조회하려면 작업 ID를 보관합니다.

Genesis는 루프백 연결을 받아들이고 Host와 Origin을 검증합니다. 요청에는 실행 인스턴스의 `mcp-token` 파일에서 가져온 bearer 자격 증명이 필요합니다. 코딩 에이전트의 호스트는 Streamable HTTP와 인증 헤더의 영구 저장을 지원해야 합니다. Genesis와 쓰기 가능한 프로젝트 디렉터리는 같은 컴퓨터에 있어야 합니다. [연결 가이드][guide]는 변경 사항이 포함된 소스 빌드 설정을 안내합니다. 출시된 서버의 설정은 [Genesis 0.14.1][related]을 참고하세요.

## 실행에 필요한 맥락을 목표에 담기

코딩 에이전트가 파서의 결함을 찾았고 회귀 테스트를 위임한다고 가정해 봅시다. 먼저 `genesis_check`로 로컬 설정을 확인한 뒤 `genesis_start_task`에 기본 체크아웃의 절대 경로와 문제가 되는 입력, 기대 동작, 실행할 테스트를 설명한 목표를 보냅니다. Genesis는 자체 설정 모델을 사용하므로 호출 측 대화에서 관련 맥락을 목표에 담아야 합니다.

아홉 가지 도구는 준비 상태, 설정 다시 불러오기, 모델 탐색, 작업 제출, 목록, 상태, 결과, 메시지, 취소를 다룹니다. 기존 Git 저장소에는 최초 커밋이 필요합니다. 이 진입점은 `.git` 디렉터리가 있는 기본 체크아웃을 요구하므로 연결된 작업 트리와 서브모듈 루트는 허용되지 않습니다. [작업 및 저장소 요구 사항][guide]

## 재연결 후 작업 ID로 추적하기

제출 결과로 받은 ID를 저장합니다. 재연결한 클라이언트는 이 ID로 `genesis_get_task`를 호출하거나 프로젝트의 최근 작업을 조회한 다음 재제출 여부를 판단할 수 있습니다. 상태에는 스케줄러와 저장된 작업 상태에서 가져온 제한된 진행 정보가 포함됩니다. 폴링할 때 전체 결과를 생략하고 변경 토큰으로 일정 시간만 기다릴 수 있습니다.

메시지 응답은 요청이 큐에 들어갔음을 확인합니다. 취소 응답은 받아들인 요청과 저장된 상태를 보여 줍니다. 실제 결과를 확인하려면 최종 상태를 읽고 `genesis_get_result`로 저장된 결과를 가져온 뒤 보고된 커밋과 테스트 증거를 검토합니다. [작업 관찰 및 제어][guide]

## 위임하기 전에 연결 확인하기

해당 리비전을 소스에서 빌드하고 실제 작업을 실행할 Genesis 인스턴스에 공급자를 설정합니다. 가이드에 따라 비공개 자격 증명을 만들고 인스턴스의 실제 루프백 주소를 클라이언트에 등록합니다. 새 클라이언트 세션에서 `genesis_check`를 호출하면 MCP 연결과 모델 준비 상태를 따로 확인한 후 작업을 제출할 수 있습니다. [설정과 연결 확인][guide]
